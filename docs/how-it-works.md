# Как это работает

## Поток выполнения задачи

```
./scripts/run-agent.sh BACK-1234 456
        │
        ▼
GigaCode CLI читает .gigacode/settings.json
        │  запускает be-tools:  npx tsx src/index.ts  (cwd: tools-server)
        ▼
be-tools: читает .env, загружает src/tools/* + dynamic/*.tool.ts → tools/list
        │
        ▼
Оркестратор backend-developer — спецификацию читает САМ, не делегируя:

  spec_get_pr(456) → spec_read_file × N → jira_get_issue(BACK-1234)
        │
        ├─ тикет в спеке ≠ переданному  ──────────► стоп, вопрос человеку
        ├─ нерешённый тред по «моему» требованию ─► стоп, вопрос человеку
        └─ спека противоречит тикету ────────────► стоп, вопрос человеку
        │
        ▼
  Определяет затронутые сервисы по спецификации и тикету:
   service_list({query}) — сверить догадку → service_checkout({service}) × N
   адрес = SERVICES_GIT_BASE + имя + "-be"  →  workspaces/<сервис>/
        │  не подтвердилось или кандидатов несколько ──► стоп, вопрос
        ▼  делегирует разведку — два субагента параллельно
   ┌────────────────────────┐   ┌────────────────────────┐
   │ docs-researcher        │   │ code-explorer          │
   │ читает базу знаний     │   │ читает код сервиса     │
   │ → правила + цитаты     │   │ → точки изменения,     │
   │   + «чего в базе нет»  │   │   аналог, тесты        │
   └───────────┬────────────┘   └───────────┬────────────┘
               └──────────────┬─────────────┘
                              ▼
  Таблица требований (R1…Rn → где реализуется → чем проверяется) + план
        │
        ▼
  ветка в каждом сервисе → правки в workspaces/<сервис>/ → тесты с ID
        │
        ▼
  ./mvnw clean verify > target/build.log   ──красная──► build-doctor
        │ зелёная                                         (читает лог,
        ▼                                                  возвращает причину)
  self-reviewer: ревью свежим взглядом → blocker / major / minor
        │
        ▼
  commit → push → draft MR в каждом сервисе, все со ссылкой на один PR аналитики
```

## Почему агент сам ищет сервисы

Выдать агенту готовый чекаут значит решить за него главный вопрос задачи — в
каком сервисе менять. На практике это и есть то, что чаще всего определяется
неверно, а цена ошибки — выброшенная работа.

Поэтому ему даётся не путь, а правило построения пути: общий префикс
`SERVICES_GIT_BASE`, суффикс `-be`, группа для API. Имя сервиса агент выводит
из спецификации и тикета, **сверяет через `service_list`** и только потом
выкачивает. Не подтвердилось или кандидатов несколько — остановка, а не
догадка.

Побочный эффект, ради которого это тоже стоило делать: задача, затрагивающая
три сервиса, перестаёт быть особым случаем. Агент выкачивает три копии, ведёт
в них одну и ту же ветку и открывает три MR с перекрёстными ссылками.

## Почему спецификация, а не тикет

Тикет пишется для планирования: приоритет, спринт, связи, сроки. Требования в
нём пересказаны, устаревают и расходятся с тем, что согласовал аналитик.
PR аналитики — версионируемый документ с историей, обсуждением и ревью. Это
единственный источник, по которому можно проверить, то ли реализовано, что
заказывали.

Отсюда трассируемость: каждому требованию присваивается `R1`, `R2`, … и этот
идентификатор проходит через план, тесты и описание MR. Ревьюер видит
соответствие «требование → код → тест» в одной таблице.

## Почему база знаний снаружи

Она ваша и общая: её сопровождает команда, из неё читают не только агенты.
Репозиторий агента её не копирует и не версионирует — только указывает путь
(`AI_DOCS_PATH`) или адрес (`AI_DOCS_GIT_URL`). Правки в базе видны агенту
сразу, без пересборки сервера инструментов.

Следствие, которое важно для роли агента: **структура базы ему заранее
неизвестна**. Он не ссылается на документы, которых не видел; он начинает с
`docs_read()`, ищет по теме и может опереться на подсказки из
`.gigacode/ai-docs-pointers.md`.

## Что где живёт

Четыре уровня, и граница между ними проведена по смыслу, а не по удобству:

| Уровень | Отвечает на вопрос | Кто наполняет |
|---|---|---|
| база знаний `ai-docs` | **что** принято в компании | команда, вне репозитория |
| скилы `.gigacode/skills/` | **как** выполнить процедуру | сам агент, через `skill_create` |
| инструменты `tools-server/dynamic/` | детерминированная операция | сам агент, через `tool_create` |
| агенты `.gigacode/agents/` | кто что видит и в каком контексте | владелец агента |

Предустановленных скилов нет, и это принципиально: скил, повторяющий документ
из базы знаний, создаёт вторую копию правила — копии разойдутся, и агент
начнёт выполнять устаревшую. Поэтому на «правила такого в базе нет» ответ не
«напишу скил», а «предложу документ в описании MR».

Скил оправдан там, где он даёт то, чего база знаний не умеет: `paths:`
включает его сам, как только работа коснулась подходящего файла, — база
знаний ждёт, пока агент догадается туда посмотреть.

## Зачем субагенты

Считайте, что съедает контекст: 5–10 документов конвенций целиком, обход кода
сервиса, простыня Maven при красной сборке. Полезный остаток от каждого —
десяток строк. Субагент читает много, возвращает выжимку, и его контекст
умирает вместе с ним.

Три следствия, которые заложены в конструкцию:

- **Спецификацию не делегируем.** Это главный артефакт; пересказ теряет
  формулировки и граничные случаи, ради которых всё и затевалось.
- **Пишет файлы только оркестратор.** У субагентов `tools` без `write_file`
  и `edit`. Иначе они разойдутся в именовании и передерутся за одни файлы.
- **`self-reviewer` ценен именно тем, что не писал код.** Свежий контекст
  здесь не экономия, а функция: он не видел обоснований автора.

Параллелизм — побочный эффект, а не цель: по-настоящему независимы только
`docs-researcher` и `code-explorer`, остальное строго последовательно.

## Почему инструментов мало

Каждый инструмент — это постоянный расход контекста (описание в `tools/list`)
и ещё одна вещь, которую нужно сопровождать. Набор покрывает то, что нельзя
сделать иначе: доступ к базе знаний, к тикету, к спецификации и возможность
расширить себя. Файлы, git и сборка уже есть во встроенном shell.

Когда агенту нужна новая операция, он решает: сделать разово через shell или
оформить инструментом. Критерии выдаёт `tool_template`, подробно —
[agent-self-extension.md](agent-self-extension.md).

## Как работает самописный инструмент

```
tool_create(name, source)
   │
   ├─ записать dynamic/<name>.tool.ts   (предыдущая версия в .bak)
   ├─ esbuild: ts → esm → .cache/<name>.<hash>.mjs
   ├─ import() и проверка структуры
   │     └─ не скомпилировалось → откат файла, инструмент не появляется
   ├─ registry.register(..., "dynamic")
   └─ notifications/tools/list_changed → клиент перечитывает tools/list
```

Хеш содержимого в имени файла кэша — то, что позволяет перезагружать модуль
без рестарта процесса: ESM-кэш Node ключуется по URL, и у новой версии URL
другой.

Инструмент остаётся файлом в репозитории, попадает в MR и проходит ревью.
Прижившиеся переносятся в `tools-server/src/tools/` как встроенные.

## Границы доверия

| Что | Кто решает |
|---|---|
| какие MCP-серверы доступны | `mcp.allowed` в `settings.json` |
| какие команды shell разрешены | `permissions`, если ваш CLI его поддерживает; иначе хук |
| может ли агент писать инструменты | `TOOLS_ALLOW_DYNAMIC` |
| снятие draft с MR, ревьюеры, статус тикета | человек |
| правки в базе знаний и в репозитории аналитики | человек |

База знаний и репозиторий аналитики открыты агенту **только на чтение**.
Агент, который сам себе переписывает требования или правила, перестаёт быть
проверяемым.

## Почему секретов нет в settings.json

`settings.json` версионируется. Удалённые MCP-серверы получают значения через
подстановку `{env:…}`, а локальный `be-tools` читает `.env` сам
(`tools-server/src/lib/config.ts`), поэтому блок с секретами ему не нужен.
