# Интеграция с GigaCode CLI: точки адаптации

Проект собран по модели конфигурации, общей для CLI-агентов: каталог
`.gigacode/` с `settings.json`, файлом проектных инструкций, ролями и
слэш-командами; инструменты подключаются как MCP-сервер по stdio.

Ниже — всё, что стоит сверить с вашей версией GigaCode CLI. Содержательная
часть (база знаний, ts-сервер, процесс) от этого не зависит.

## 1. Имя и расположение файла настроек

Ожидается `.gigacode/settings.json` в корне проекта. Если ваш CLI читает
другое имя (`config.json`, `.gigacoderc`) или другой каталог — переименуйте;
содержимое не меняется.

```bash
gigacode --help | grep -i -E 'config|settings|mcp'
```

## 2. Схема подключения MCP-сервера

Используется распространённая форма:

```json
{
  "mcpServers": {
    "ai-tools": { "type": "stdio", "command": "bash", "args": ["scripts/start-tools-server.sh"] }
  }
}
```

Встречающиеся варианты ключа: `mcpServers`, `mcp.servers`, `servers`, `tools`.
Если отличается — поменяйте только обёртку. Сам сервер — стандартный MCP over
stdio и совместим с любым клиентом; проверить его отдельно:

```bash
cd tools-server && npm run inspect
```

Инспектор покажет `tools/list` и даст вызвать любой инструмент руками. Если
там всё работает, а в GigaCode нет — проблема в форме записи в `settings.json`,
а не в сервере.

## 3. Рабочий каталог при запуске сервера

`args` содержит относительный путь `scripts/start-tools-server.sh`, который
подразумевает, что сервер стартует из корня проекта. Если ваш CLI запускает
процесс из другого каталога — замените на абсолютный путь. Сам скрипт
определяет корень от своего расположения и не зависит от `cwd`.

## 4. Передача переменных окружения

Сервер берёт конфигурацию из окружения и читает `.env` сам, поэтому
подстановка вида `${JIRA_TOKEN}` в `settings.json` не требуется — это
сознательное решение, см. `docs/how-it-works.md`. Если ваш CLI такую
подстановку умеет, можно перенести значения в `env`, но тогда не коммитьте
`settings.json` с секретами.

## 5. Файл проектных инструкций

`.gigacode/AGENTS.md` — текст, который должен подгружаться в каждую сессию.
Частые альтернативные имена: `GIGACODE.md`, `rules.md`, `system.md`,
`instructions.md`. Если имя другое — переименуйте; на содержание это не влияет.
Внутри файл ссылается на `.gigacode/agents/backend-developer.md`, поэтому даже
при отсутствии поддержки «ролей» агент получит процедуру по ссылке.

## 6. Роли и слэш-команды

`.gigacode/agents/*.md` с YAML-frontmatter (`name`, `description`, `tools`) и
`.gigacode/commands/*.md` (`description`, `argument-hint`, подстановка
`$ARGUMENTS`) — распространённый формат. Если он не поддерживается:

- содержимое `agents/backend-developer.md` перенесите в `AGENTS.md`;
- вместо `/ticket BACK-1234` передавайте текст команды как промпт —
  `scripts/run-agent.sh` для этого и нужен, достаточно поправить в нём
  последнюю строку.

## 7. Permissions

`permissions.allow` / `permissions.deny` с шаблонами `Bash(git push:*)` и
`mcp__<сервер>__<инструмент>` — тоже конвенция конкретного CLI. Если имена
встроенных инструментов отличаются (`Shell` вместо `Bash`, `ReadFile` вместо
`Read`), поправьте шаблоны. **Список `deny` важнее `allow`:** он защищает от
force-push, чтения ключей и записи в `ai-docs`.

## 8. Уведомление `tools/list_changed`

Сервер шлёт его после `tool_create`, чтобы созданный инструмент стал виден без
рестарта. Если клиент уведомление игнорирует, инструмент всё равно
зарегистрирован — достаточно перезапустить сессию (или клиент сам перечитает
список перед следующим вызовом). Проверяется это одной командой:

```bash
cd tools-server && npm run smoke
```
