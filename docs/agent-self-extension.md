# Как агент расширяет себя

Агент стартует с минимальным набором: чтение базы знаний, чтение тикета,
чтение PR аналитики и «кузница». Ни одного предустановленного скила, ни
одного инструмента сверх необходимого. Всё остальное он делает руками — до
тех пор, пока операция не начнёт повторяться.

Эти правила продублированы в выдаче `tool_template` и `skill_create`, поэтому
агент видит их в момент, когда они нужны, и не зависит от того, есть ли такой
текст в вашей базе знаний.

## Три разных ответа на «мне чего-то не хватает»

| Что заметил агент | Чем закрывается | Где окажется |
|---|---|---|
| механическая операция с чётким входом и выходом | инструмент | `tools-server/dynamic/<name>.tool.ts` |
| повторяющаяся последовательность шагов, требующая суждения | скил | `.gigacode/skills/<name>/SKILL.md` |
| правило компании, которого нет в базе знаний | **ничего не создаётся** | раздел «решения вне базы знаний» в описании MR |

Третья строка — главная. Правило, скопированное в скил или в инструмент,
разойдётся с базой знаний, и агент начнёт выполнять устаревшую версию.
Поэтому скил ссылается на документ базы, но не пересказывает его.

# Инструменты

## Когда создавать инструмент

Создавать, если выполняется хотя бы два условия:

- операция повторится в следующих тикетах;
- она механическая и имеет чёткий вход/выход;
- выполнение вручную требует больше трёх шагов или разбора сырого ответа API.

Уместные примеры: открыть MR, получить отчёт о покрытии, сходить во внутренний
реестр сервисов, распарсить surefire-отчёт, выгрузить схему события из реестра.

## Когда НЕ создавать

- Одноразовое действие в рамках одного тикета — проще `bash`.
- Операция требует суждения (выбор архитектуры, формулировка описания MR).
- Такой инструмент уже есть — проверяется через `tool_list`.
- Инструмент потребовал бы захардкоженного секрета.

## Порядок

1. `tool_list` — убедиться, что такого ещё нет.
2. `tool_template` — получить актуальный скелет модуля.
3. `tool_create` — передать `name` и полный исходник.
4. Вызвать инструмент. Не то поведение — `tool_create` с `overwrite: true`.

Сервер компилирует модуль и импортирует его **до** регистрации: если он не
собирается, файл откатывается, инструмент не появляется, а агент получает
текст ошибки компиляции.

## Требования к инструменту

- Одна ответственность, `snake_case`-имя.
- У каждого поля `inputSchema` — `.describe()`: это единственное, что видит
  модель.
- Секреты только из `ctx.config` (сервер читает окружение), никогда в коде.
- Ничего не писать в stdout — там протокол MCP; логировать через `ctx.logger`.
- Разрушающее действие помечается `annotations.destructiveHint: true`.

## Инструмент — это код

Файл появляется в `tools-server/dynamic/<name>.tool.ts` и попадает в тот же MR,
что и изменения сервиса. Он проходит обычное ревью. Прижившиеся инструменты
переносятся в `tools-server/src/tools/` как встроенные.

Выключить: `TOOLS_ALLOW_DYNAMIC=false` в `.env`.

## Пример

```ts
import { defineTool, failure, text, z } from "./_sdk.js";

export default defineTool({
  name: "jacoco_summary",
  description: "Прочитать target/site/jacoco/jacoco.csv и вернуть покрытие по пакетам.",
  annotations: { readOnlyHint: true },
  inputSchema: z.object({
    service: z.string().describe("Имя сервиса, как его вернул service_checkout."),
    module: z.string().optional().describe("Подкаталог модуля, если проект многомодульный."),
  }),
  async handler(input, ctx) {
    const { readFile } = await import("node:fs/promises");
    const root = `${ctx.config.services.workspacesDir}/${input.service}`;
    const path = `${root}/${input.module ?? "."}/target/site/jacoco/jacoco.csv`;
    try {
      return text(await readFile(path, "utf8"));
    } catch {
      return failure(`Нет отчёта: ${path}. Сначала запусти ./mvnw verify.`);
    }
  },
});
```

Рабочий пример в репозитории — `tools-server/dynamic/create_merge_request.tool.ts`.

# Скилы

Скил — это процедура: порядок шагов, что должно получиться, когда
остановиться. В отличие от инструмента он не выполняет операцию, а задаёт
способ работы.

## Когда создавать

- последовательность шагов повторится в следующих задачах;
- её нет в базе знаний как документа;
- либо она привязана к типу файлов — тогда `paths:` включит скил сам, как
  только работа коснётся подходящего файла. Этого база знаний не умеет, и это
  главная причина, по которой скилы вообще нужны.

## Когда НЕ создавать

- Это правило компании. Ему место в базе знаний: предложи документ в описании
  MR, а не копируй текст в конфигурацию агента.
- Процедура одноразовая, в рамках одной задачи.
- Операция детерминированная и без суждения — нужен инструмент, не скил.

## Порядок

1. `skill_create` без аргументов — шаблон, критерии и список существующих
   скилов.
2. `skill_create` с `name` и `source`.

Перед записью проверяются frontmatter, совпадение `name` с именем каталога и
лимиты (description 1000, тело 10000 символов). Не прошло — файл не создаётся.
Отдельно ловится двоеточие внутри незакавыченного значения: оно молча ломает
YAML, и скил просто не загрузился бы.

## Важное отличие от инструментов

Инструмент подхватывается на лету. **Скил — нет**: он станет доступен со
следующей сессии. В текущей задаче агент продолжает по шагам, которые только
что записал.

Выключить: `SKILLS_ALLOW_CREATE=false` в `.env`.
