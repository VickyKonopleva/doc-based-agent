# Spec-driven разработка: работа с PR аналитики

> Черновик для вашей базы знаний. Приведите `id`, `type` и ссылки в конце к
> принятым у вас именам, затем добавьте документ в `INDEX.md`.

## Модель

Требования живут в репозитории спецификаций (SA specification). Системный
аналитик открывает PR, в котором описывает задачу: требования, контракты,
схемы событий, диаграммы, критерии приёмки.

```
аналитик ──► PR в репозиторий аналитики ──► разработка ──► MR в сервис
             (что делать)                                  (как сделано)
```

**Тикет Jira — не ТЗ.** Он даёт контекст: приоритет, спринт, связи, сроки,
историю обсуждения. Что именно реализовать — говорит спецификация.

## Приоритет источников требований

```
PR аналитики  >  тикет Jira  >  существующий код
```

Содержательное противоречие между спекой и тикетом **не разрешается
разработчиком** — это стоп-ситуация и вопрос аналитику.

## Порядок чтения

1. `spec_get_pr(<PR>)` — описание, список файлов, обсуждение.
2. `spec_read_file({ pr, path })` по **каждому** файлу спецификации, целиком.
   Описание PR и список файлов — это оглавление, а не требования.
3. Для файлов со статусом `modified` — ещё и `mode: "diff"`: видно, что
   аналитик изменил в этой итерации и на что смотреть внимательнее.
4. Сверить: тикет, упомянутый в PR, совпадает с переданным номером.
5. Прочитать обсуждение PR.

## Трассируемость требований

Каждому требованию спецификации присваивается идентификатор (`R1`, `R2`, …;
если аналитик их не проставил — нумеруй сам и скажи об этом). Дальше этот
идентификатор проходит через всю работу:

| Где | Как выглядит |
|---|---|
| план | строка таблицы требований |
| код | комментарий у неочевидной реализации: `// R3: событие публикуется ровно один раз` |
| тест | имя или `@DisplayName`: `shouldPublishFailedEvent_whenRetriesExhausted // R3` |
| описание MR | таблица «требование → где реализовано → чем покрыто» |

Таблица требований в плане и в MR:

| ID | Требование | Приоритет | Где реализуется | Чем проверяется | Статус |
|----|-----------|-----------|-----------------|-----------------|--------|
| R1 | ретраи 1s/2s/4s + джиттер | must | `PaymentCallbackService` | `…Test#shouldRetryWithBackoff` | сделано |
| R4 | метрика попыток | should | `CallbackMetrics` | `…IT#shouldCountRetries` | сделано |
| R5 | таймаут 5s | must | `GatewayProperties` | — | **вне рамок, см. ниже** |

Требование со статусом `must`, оставшееся нереализованным, — это незакрытая
задача. Такое указывается в описании MR явно, а не умалчивается.

## Нерешённые треды

Нерешённый тред обсуждения по требованию, которое ты реализуешь, — **стоп**.
Его смысл: аналитик и заказчик ещё не договорились. Код, написанный по
недоговорённому требованию, переделывается.

Нерешённый тред по требованию вне твоих рамок — не блокирует; упомяни его в MR.

## Пробелы и противоречия в спецификации

Спецификация неполна почти всегда. Порядок:

1. Проверить, не закрывается ли пробел конвенцией из `ai-docs` — например,
   формат ошибки или пагинация описаны в вашей конвенции по REST, и аналитику
   незачем их дублировать. Это **не** пробел.
2. Если не закрывается — сформулировать допущение одной фразой, записать его
   в раздел «Допущения» плана и в описание MR.
3. Если допущение меняет наблюдаемое поведение системы (контракт, статусы,
   поведение при ошибке) — **не допускать, а спрашивать**.

## Состояние PR аналитики

| Состояние | Что делать |
|---|---|
| open, треды решены | работать |
| open, есть нерешённые треды по твоим требованиям | стоп, вопрос |
| draft / черновик | стоп: спецификация ещё не готова |
| merged | работать; это согласованная версия |
| closed | стоп: задача, скорее всего, отменена |

## Если спецификации нет

Задача не берётся. Исключение — инцидент или хотфикс, когда ждать спеку
нельзя: тогда работа ведётся по тикету, а в описании MR появляется раздел
«Работа без спецификации» с перечнем принятых решений и задачей аналитику
описать их постфактум.

## Нельзя

- Начинать реализацию, прочитав только описание PR и не открыв файлы.
- Реализовывать «по смыслу тикета», когда спека говорит иначе.
- Молча расширять рамки: сделать больше, чем требует спека, — тоже отклонение.
- Править спецификацию: репозиторий аналитики открыт только на чтение.
- Считать нерешённый тред несущественным.
