# Жизненный цикл тикета

Единственный вход агента — номер тикета Jira (например `BACK-1234`). Всё
остальное агент добывает сам.

## Фаза 1. Разведка (ничего не меняем)

1. `docs_read` без аргументов — карта базы.
2. `jira_get_issue(TICKET)` — summary, description, acceptance criteria,
   компоненты, метки, связанные тикеты, последние комментарии.
3. Определить **затронутый сервис**: по полю `components`, по префиксу
   проекта, по упоминанию в тексте. Прочитать `40-projects/<сервис>.md`.
   Если сервис определить не удалось — остановиться и спросить человека.
4. `docs_search` по ключевым терминам тикета (и по русским, и по английским).
5. Прочитать найденные конвенции целиком, а не по сниппетам.

Результат фазы — понимание: что меняем, в каком сервисе, по каким правилам.

## Фаза 2. План

Короткий план в ответе пользователю, до правок:

- список файлов, которые будут созданы или изменены;
- какие конвенции применяются (с `id` документов);
- что останется за рамками;
- открытые вопросы и принятые допущения.

Если в тикете нет acceptance criteria и их нельзя вывести из описания —
не угадывать: сформулировать своё понимание критериев и явно пометить как
допущение.

## Фаза 3. Ветка

По `10-process/branching-and-commits.md`. Ветка создаётся от актуального
целевого бранча, а не от текущего состояния рабочей копии.

## Фаза 4. Реализация

- Сначала контракт (API/схема/событие), потом реализация, потом тесты.
- Каждое изменение сверяется с `30-conventions/*`.
- Миграции БД — только через Liquibase, см. `30-conventions/persistence.md`.
- Новые зависимости не добавлять без явного указания в тикете.

## Фаза 5. Проверка

Локально и обязательно:

```bash
./mvnw -q clean verify
```

Сборка должна быть зелёной. Падающий тест не «чинится» его удалением или
`@Disabled` — см. `30-conventions/testing.md`.

## Фаза 6. Коммит и MR

1. Коммиты по `10-process/branching-and-commits.md`.
2. `git push -u origin <branch>`.
3. MR по `10-process/merge-request.md` — создаётся **draft**.
4. Проверить себя по `10-process/definition-of-done.md` и
   `10-process/code-review-checklist.md`.

Агент не переводит тикет в другой статус и не назначает ревьюеров —
это делает человек.

## Когда останавливаться и спрашивать

- Не определён сервис или модуль.
- Тикет требует изменения публичного контракта, не описанного в тикете.
- Требуется новая внешняя зависимость или новый сервис.
- Нужны права/секреты, которых нет в окружении.
- Найденное правило в `ai-docs` прямо противоречит тексту тикета.

## Нельзя

- Начинать правки до фазы 1.
- Переписывать чужой код «заодно».
- Трогать файлы вне затронутого сервиса.
- Коммитить секреты, `.env`, локальные конфиги.
- Делать `git push --force` в общие ветки.
