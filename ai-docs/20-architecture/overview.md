# Архитектурный ландшафт

> Раздел описывает целевое состояние. Отклонения конкретного сервиса
> фиксируются в его карточке в `40-projects/`.

## Стиль

Набор самостоятельных Spring Boot сервисов, каждый со своей БД. Общение:

- **синхронно** — REST поверх HTTP/JSON, только когда нужен ответ здесь и сейчас;
- **асинхронно** — события в Kafka, по умолчанию для всего остального.

Общая БД между сервисами запрещена. Сервис владеет своими данными и отдаёт их
только через контракт.

## Границы

Границу сервиса определяет бизнес-способность, а не сущность. Если изменение
требует одновременной правки трёх сервисов — границы проведены неверно, это
повод для ADR, а не для «быстрого» кросс-сервисного вызова.

## Слои внутри сервиса

См. `20-architecture/service-layering.md`.

## Поперечные требования

Любой сервис обязан предоставлять:

- `/actuator/health` (liveness + readiness) и `/actuator/prometheus`;
- структурированные логи с `traceId` (`conv-observability`);
- graceful shutdown;
- таймауты на все исходящие вызовы;
- миграции схемы через Liquibase.

## Запреты уровня ландшафта

- Прямое обращение к чужой БД.
- Синхронная цепочка длиннее двух сервисов на пользовательском запросе.
- Бизнес-логика в контроллере или в репозитории.
- Общий «core»-модуль с бизнес-логикой нескольких доменов.
