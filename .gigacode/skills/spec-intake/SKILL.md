# Разбор спецификации

Процедура превращения PR аналитики в таблицу требований, по которой дальше
пишутся код, тесты и описание MR.

Спецификацию читает основной агент, **не делегируя** субагентам: пересказ
теряет формулировки и граничные случаи, ради которых всё и затевалось.

## Шаги

1. `spec_get_pr(<PR>)` — описание, список файлов, обсуждение, упомянутые
   тикеты.
2. `spec_read_file({ pr, path })` по **каждому** файлу из раздела «Файлы
   спецификации», целиком. Список файлов и описание PR — оглавление, а не
   требования.
3. Для файлов со статусом `modified` дополнительно `mode: "diff"`: видно, что
   аналитик изменил в этой итерации и на что смотреть внимательнее.
4. Сверить тикет, упомянутый в PR, с переданным номером.
5. Прочитать обсуждение целиком.
6. Присвоить требованиям идентификаторы. Аналитик проставил `R1`, `R2` —
   используем их; не проставил — нумеруем сами и сообщаем об этом человеку.

## Результат

| ID | Требование | Приоритет | Источник | Критерий приёмки |
|----|-----------|-----------|----------|------------------|
| R1 | …         | must      | `payments/callback-retry.md`, раздел «Требования» | … |

Плюс отдельно:

- **вне рамок** — что спецификация явно исключает;
- **допущения** — то, что пришлось доформулировать, если критериев приёмки
  нет;
- **пробелы** — где текст не позволяет реализовать однозначно.

Прежде чем назвать что-то пробелом, проверь, не закрывается ли это
конвенцией из базы знаний: формат ошибки, пагинация, формат логов аналитику
дублировать незачем. Это **не** пробел.

## Стоп-ситуации

Останавливайся и спрашивай человека:

- PR недоступен или не содержит файлов спецификации;
- тикет в спеке не совпадает с переданным;
- в PR есть нерешённый тред по требованию, которое предстоит реализовать:
  аналитик и заказчик ещё не договорились, и код придётся переделывать;
- спецификация противоречит тикету по существу;
- пробел меняет наблюдаемое поведение системы — контракт, статусы, поведение
  при ошибке. Такое не додумывают.

## Состояние PR

| Состояние | Что делать |
|---|---|
| open, треды решены | работать |
| open, нерешённые треды по твоим требованиям | стоп |
| draft | стоп: спецификация ещё не готова |
| merged | работать, это согласованная версия |
| closed | стоп: задача, скорее всего, отменена |
